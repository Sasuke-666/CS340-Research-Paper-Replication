# Why the twostage reader can see half an update

He Boyu (何博宇), 1240000576, `heboyu0714` · 15 November 2026  
Team baseline `fd0d807f39a9d972dcd4929486d002f53ae4e4f3` · [Original C source](https://github.com/wcventure/PERIOD/blob/cb8deb9a176e5bb292d70d46557dd61dc0e98069/evaluation/CS/twostage/twostage_bad.c) · [Execution trace table](1240000576-twostage-trace.md) · [Replay record](../../results/member-reruns/1240000576-twostage-43681034375/README.md)

In the default two-worker case, one thread publishes two related integers in separate critical sections. A reader can pass the first-value check and still read the old second value. The archive identifies this outcome in PERIOD run 1, schedule 4. On a fresh Linux runner, the unchanged replay driver triggered the same source assertion on all five attempts with that witness. The evidence establishes the inconsistent values under the source semantics, while leaving the fine-grained execution order open.

## What the paper measured

Wen et al. list `CS.twostage_bad` in Table 2 as an SCTBench assertion failure with two subthreads and bug depth 2. The PERIOD and Serial columns each report 4 schedules through the first failure, 33 schedules explored, and 3 failing schedules. Section 4.1.3 gives a depth bound of 3 for this benchmark suite, a 10,000-schedule budget and ten invocations. These metrics describe exploration. A witness replay tests a single input under a fresh calibration. [Paper, sections 4.1.3–4.2 and Table 2, PDF pp. 8–9](https://wcventure.github.io/pdf/ICSE2022_PERIOD.pdf#page=9)

Field 2 could subsequently change while B still holds its local copy. |

The property that needs synchronization is the relationship between the two values. Locking each field separately permits a partially published pair to become visible. A design that requires coherent snapshots could publish both fields under one mutex and have the reader copy both under that same mutex.

## PERIOD and the compatible serialized driver

PERIOD selects `SBPMESched`, which permits multiple threads in the last period. The compatible serialized driver selects `SBPSched` and assigns a single thread per period. In the selected pair, both drivers printed the same 33 schedule descriptions in the same order and reported failures on IDs 4 and 17. The first serialized witness also records the line-48 assertion. Here the algorithmic distinction produced no reduction in the printed search space. ## Independent replay and scope

The team repository was freshly cloned from main at `fd0d807f39a9d972dcd4929486d002f53ae4e4f3`. A branch-only job checked out the replay setup, fetched the authors’ pinned source and rebuilt the analysis, instrumentation and target in the pinned container. The rebuilt executable’s SHA-256 matches the archived binary. Five predeclared consecutive calls replayed exactly one archived input, with the stock driver, no target arguments and no changes to the original C. All five produced the matching assertion after the reproduction marker. The warning about resolving the container hostname also appears in the archive. A driver exit of zero alone cannot classify the target result because this replay path ends with a bare `sys.exit()`. These five observations establish repeatability on this build and host for the selected witness. They do not measure an unconditional failure probability or prove a unique instruction-by-instruction trace. The archive and new replay use different host processors. The archive’s comparison also varies across repetitions, even when requested schedules agree.
